## 지금 상태

- 브랜치: !`git branch --show-current`
- status: !`git status --short`
- 스테이지된 것: !`git diff --cached --stat`
- 스테이지 안 된 것: !`git diff --stat`
- 변경 내용: !`git diff HEAD | head -c 60000`
- 최근 커밋 5개 (문체 표본, 본문 포함): !`git log -5 --format='--- %s%n%b'`

사용자가 준 힌트: $ARGUMENTS

## 할 일

커밋 하나를 만든다. **push 하지 않는다.**

### 1. 커밋할 것을 고른다

- 이미 스테이지된 것이 있으면 **그것만** 커밋한다. 의도적으로 고른 것으로 본다.
- 스테이지가 비어 있으면 관련된 파일만 골라 `git add` 한다. `git add -A` 로 뭉뚱그리지 않는다.
- 위 diff 가 `head -c` 로 잘렸으면 필요한 파일만 `git diff <경로>` 로 다시 본다.

**커밋에 넣지 않는다** — 발견하면 담지 말고 사용자에게 알린다:
`.env*`, 자격증명·토큰·비밀키가 든 파일, 빌드 산출물, 지금 작업과 무관한 변경.

관심사가 뚜렷이 둘 이상 섞여 있으면, 커밋하기 전에 나눌지 먼저 묻는다.

### 2. 메시지를 쓴다

**문체는 위 `git log` 표본에서 가져온다.** 접두사(`feat:` 같은 것), 언어, 시제,
본문 유무 — 전부 이 저장소가 하던 대로 맞춘다. 표본이 없는 새 저장소일 때만
`type: 요약` 형태를 기본으로 쓴다. 타입은 `feat fix docs refactor test chore`.

**스코프를 쓰지 않는다.** `feat(auth):` 가 아니라 `feat:` 다. 표본이 스코프를
쓰고 있을 때만 따라간다.

제목은 마침표 없이, 72자 안에서 끝낸다.

- 제목은 **무엇을 왜** 바꿨는지. 파일 목록이나 구현 나열이 아니다.
- 본문은 표본이 본문을 쓸 때만 쓴다. 쓴다면 **왜 그랬는지**와 근거를 적는다 —
  무엇이 어떻게 틀렸었는지, 확인한 수치, 남은 문제, 일부러 하지 않은 것.
- 사소한 변경은 제목 한 줄로 끝낸다. 없는 사연을 지어내지 않는다.
- 확인하지 않은 것을 확인한 것처럼 쓰지 않는다. 검사를 돌렸으면 결과를 그대로,
  안 돌렸으면 적지 않는다.

이 세션 지침에 커밋 attribution(`Co-Authored-By:` 등)이 지정돼 있으면 그대로 붙인다.
지침에 없으면 붙이지 않는다 — 옛 세션 URL 을 기억해서 쓰지 않는다.

### 3. README 가 어긋났는지 본다

README 는 **무엇이 어떻게 돼 있는지**를 설명하는 문서다. 이번 변경이 그 설명을
틀리게 만들었으면 같은 커밋에서 함께 고친다. 따로 커밋하면 그 사이 README 가
거짓말을 한다.

고치는 경우 — 이번 diff 가 아래를 건드렸을 때만이다:

- `package.json` 의 scripts, Makefile 타깃 등 **사람이 치는 명령**이 늘거나 바뀜
- 환경변수, 설정 파일, 필수 준비물이 늘거나 이름이 바뀜
- 설치·실행·배포 **절차**가 바뀜
- 최상위 디렉터리나 진입점이 생기거나 사라짐
- README 가 이름을 대며 설명하던 파일·기능이 사라지거나 옮겨감

**고치지 않는 경우** — 내부 리팩터링, 버그 수정, 스타일 변경, README 가 애초에
언급하지 않는 것. 이런 것까지 반영하려 들면 README 가 변경 이력이 된다.

- **변경 이력을 README 에 쌓지 않는다.** 그건 git log 가 한다.
- **통째로 다시 쓰지 않는다.** 어긋난 줄만 고친다. 표가 있으면 표의 그 행만.
- 문서의 말투와 구성을 그대로 따른다. 새 절을 함부로 만들지 않는다.
- **diff 에서 확인한 것만 적는다.** 동작을 짐작해서 쓰지 않는다.
- 고쳤으면 `git add` 해서 이번 커밋에 포함시키고, 무엇을 고쳤는지 보고에 적는다.
- 고쳐야 할지 애매하면 **손대지 말고** 어디가 의심스러운지만 알린다.

저장소에 `CLAUDE.md`/`AGENTS.md` 가 있으면 그쪽의 문서 규칙이 위보다 우선한다.

### 4. 커밋 전 검사

저장소의 `CLAUDE.md`(또는 `AGENTS.md`)에 "커밋 전" 검사가 적혀 있으면 먼저 돌린다.
실패하면 **커밋하지 말고** 결과를 보고한다.

조건이 붙은 검사(마크다운을 건드렸을 때만 같은 것)는 해당할 때만 돌린다.

이 대화에서 이미 돌려 통과했고 **그 뒤로 코드가 바뀌지 않았으면 다시 돌리지 않는다.**
대신 언제 통과했는지, 어느 검사를 왜 건너뛰었는지 밝힌다 — 밝히지 않으면 읽는 쪽이
통과한 것과 안 돌린 것을 구분할 수 없다.

### 5. 보여주고 확인을 받는다

커밋 **전에** 메시지를 코드블록으로 그대로 보여준다. 안에 백틱이나 `@` 같은
군더더기 구분자를 덧대지 않는다. 함께 한 줄로 알린다 — 담은 파일 수,
README 를 고쳤는지, 검사 결과(또는 언제 통과했는지).

그리고 **"이 메시지로 커밋할까요? (y/n)"** 라고 묻고 멈춘다.

- `y` / 예 → 커밋한다.
- `n` / 아니오 / 수정 요청 → 고쳐서 다시 보여주고 다시 묻는다.
- **확인 전에는 `git commit` 을 부르지 않는다.**

### 6. 커밋한다

pre-commit 훅이 파일을 고치거나 실패하면, `--no-verify` 로 우회하거나 조용히
`--amend` 하지 않는다. 무슨 일이 났는지 보고하고 지시를 기다린다.

끝나면 `git log -1 --stat` 로 결과 한 번만 보여준다.
