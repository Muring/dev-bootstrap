# 코드 전체 점검

현재 작업 중인 저장소를 아래 11개 관점으로 점검한다. 변경분만 리뷰하는 명령이 아니다.
사용자의 중점 사항: $ARGUMENTS

Claude Code에서는 `/code-audit`, Codex에서는 `$code-audit`로 호출한다.
Codex에서 `$ARGUMENTS`는 자동 치환 변수가 아니라 호출과 함께 전달한 중점 사항을 뜻한다.
추가 입력이 없으면 전체 점검을 수행한다. 명령 파일이 저장된 위치가 아니라 사용자가
현재 작업 중인 저장소를 대상으로 한다.

입력은 점검의 우선순위와 깊이를 조정한다. 사용자가 명시적으로 범위를 제한하지 않으면
나머지 관점과 코드 영역도 확인한다. 저장소 위치가 불분명하면 먼저 확인한다.

## 기본 원칙

- 기본 동작은 **점검과 대화 내 보고**다. 코드·설정·문서·데이터를 수정하지 않는다.
- 패키지 설치, 자동 수정 옵션, 코드 생성, 마이그레이션, 커밋·푸시·배포를 실행하지 않는다.
- 수정이 필요하면 근거와 수정 방향을 보고한다. 실제 수정은 별도 요청으로 진행한다.
- 저장소 지침과 현재 세션의 권한·계획 모드·자료 반출 제한을 따른다.
- 비밀정보나 개인정보를 결과에 복사하지 않는다. 외부 서비스에 소스나 데이터를 업로드하지 않는다.
- 특정 프레임워크나 디렉터리 구조를 가정하지 않는다. 프로젝트 특성에 맞춰 기준을 적용한다.

## 1. 범위와 구조 파악

1. 적용되는 AGENTS.md·CLAUDE.md, README, 패키지·빌드·테스트 설정을 확인한다.
2. 기술 스택, 주요 진입점, 화면·API·도메인 로직·데이터 접근·공통 UI·테스트·스크립트 등
   실제 코드 영역과 의존 관계를 목록화한다. 탐색은 rg와 rg --files를 우선한다.
3. 외부 패키지와 생성물은 직접 코드 검토에서 제외한다. 잠금 파일과 생성 설정은
   의존성·재현성 판단에 필요한 만큼 확인한다. 숨김 설정도 관련 있는 것만 확인한다.
4. 점검할 영역과 사용할 검증 방법을 짧게 알린 뒤 진행한다.

## 2. 11개 점검 기준

### 1) 중복 코드
- 컴포넌트·스타일·데이터 처리·검증·오류 처리의 중복을 찾는다.
- 모양만 비슷한 코드와 같은 책임을 가진 중복을 구분하고, 함께 변경되어야 하는지 확인한다.

### 2) 재사용과 추상화
- 버튼·드롭다운·태그 등 공통 요소와 공통 로직이 실제로 재사용되는지 확인한다.
- 과도한 옵션·간접 계층·추상화로 이해나 변경이 어려운 부분도 확인한다.
- 공통화는 의미와 변경 이유가 같고 유지보수 효과가 있을 때만 제안한다.

### 3) 불필요한 코드
- 미사용 파일·함수·타입·스타일·패키지, 도달하지 않는 분기, 임시 코드와 낡은 주석을 찾는다.
- 검색 결과만으로 미사용을 확정하지 않는다. 동적 import, 자동 라우팅, 설정·스크립트 참조,
  공개 export 등 실제 사용 경로를 확인하고 불확실하면 삭제 후보로만 표시한다.

### 4) 구조와 책임 분리
- 모듈의 응집도와 결합도, 거대한 컴포넌트·함수, 순환 의존을 확인한다.
- 화면·비즈니스 로직·데이터 접근의 경계와 변경 영향 범위가 적절한지 확인한다.

### 5) 기능 정확성
- 핵심 사용자 흐름과 검색·정렬·필터·페이지 이동·집계 등의 경계 조건을 확인한다.
- 날짜·시간대·빈 값·중복 값, DB 제약조건·트랜잭션·삭제 정책 등 데이터 무결성을 확인한다.

### 6) 상태 관리와 화면 전환
- URL·서버·클라이언트 상태의 동기화, 비동기 응답 순서, 오래된 상태 사용을 확인한다.
- 불필요한 재마운트·깜박임, 입력 조합(한글 IME 등), 뒤로 가기·앞으로 가기를 확인한다.

### 7) SSR과 성능
- 해당하는 프로젝트에서는 서버·클라이언트 경계, hydration, 캐시와 무효화를 확인한다.
- DB 쿼리·N+1·불필요한 요청, 번들·이미지·렌더링 비용을 확인한다.
- 측정하지 않은 병목은 확정하지 않고 추정 근거와 검증 방법을 제시한다.

### 8) 디자인 일관성과 접근성
- 기본·호버·선택·포커스·비활성 상태의 일관성과 스타일 우선순위를 확인한다.
- 상호작용 가능한 요소의 피드백과 정적 정보의 표현을 구분한다.
- 간격·높이·테두리·반응형, 긴 콘텐츠, 시맨틱 요소·접근 가능한 이름·키보드 조작·대비를 확인한다.
- 코드만 읽은 판단과 실제 화면에서 검증한 결과를 구분한다.

### 9) 보안과 데이터 보호
- 인증·서버 측 권한 검증·입력 검증·콘텐츠 렌더링·업로드·정보 노출을 확인한다.
- 프로젝트에 해당하는 인젝션·XSS·CSRF·SSRF 위험과 의존성 보안 문제를 확인한다.
- 취약점과 지원 상태는 버전 및 확인 가능한 근거를 명시하고, 확인하지 못하면 단정하지 않는다.
- 운영 데이터 변경이나 공격성 요청을 이용한 검증은 수행하지 않는다.

### 10) 오류 처리와 안정성
- 로딩·빈 데이터·실패 상태와 사용자 피드백, 재시도·취소·복구 동작을 확인한다.
- 중복 제출·연속 클릭·동시 요청·부분 실패·삭제 실패 시 일관성을 확인한다.

### 11) 테스트와 유지보수
- 중요한 동작과 회귀 위험을 검증하는 테스트가 있는지, 테스트가 구현을 그대로 복제하지 않는지 확인한다.
- 타입 안전성, 설정·스크립트·관련 문서와 실제 동작의 일치 여부를 확인한다.
- 테스트 수나 스타일 취향만으로 문제를 만들지 않는다. 변경 안전성과 이해 비용을 기준으로 판단한다.

## 3. 검증과 판단

- 발견 사항은 호출부·사용처·설정·관련 테스트를 확인하여 근거를 보강한다.
- 검사 실행 전에 스크립트와 전후처리를 읽는다. 소스·추적 파일·DB·외부 서비스에 변경을
  일으키는 검사는 실행하지 않는다. 캐시나 임시 빌드 산출물만 만드는 검사는 가능하다.
- 사용 가능한 기존 lint·타입 검사·테스트 등을 필요에 맞게 실행한다. build가 추적 파일을
  변경하거나 코드 생성·외부 데이터 변경을 포함하면 건너뛰고 제한을 보고한다.
- 기존 도구가 없으면 자동 설치하지 않는다. 점검을 위해 별도 테스트 파일을 작성하지 않는다.
- 기존 실패와 이번 점검으로 확인한 문제를 구분하고, 성공·실패·미실행을 정확히 기록한다.
- 실행이나 화면 검증이 불가능한 항목은 정적 검토의 한계를 밝힌다.
- 검토하지 않은 영역을 정상으로 표시하지 않는다. 큰 저장소도 일부 표본 검토를 전체 검토로 표현하지 않는다.

## 4. 결과 보고

한국어로 다음 순서로 보고한다. 같은 원인의 발견 사항은 묶고, 개수를 채우기 위한 제안은 하지 않는다.

1. **핵심 결과**: 중요한 결함과 위험을 먼저 설명한다. 발견하지 못한 경우에도 점검 한계를 함께 밝힌다.
2. **발견 사항**: 실제 결함·위험 → 구조 개선 → 선택적 정리 순서로 정리한다.
   각 항목에 다음 내용을 포함한다.
   - 분류와 심각도(치명적·높음·보통·낮음), 확인 상태(확인됨·추가 검증 필요)
   - 파일 위치와 줄 번호, 코드 근거 또는 재현 조건
   - 사용자·데이터·유지보수에 미치는 영향과 관련 사용처
   - 권장 수정 방향, 예상 수정 규모(소·중·대), 주의할 회귀 위험
3. **점검 범위**: 11개 관점별로 확인한 영역과 상태(검토 완료·부분 검토·미확인·해당 없음)를
   표로 요약한다. 부분 검토·미확인·해당 없음에는 이유를 적는다.
4. **검증 결과**: 실행한 검사와 결과, 실행하지 못한 검사, 남은 불확실성을 적는다.
5. **권장 순서**: 효과와 위험에 따라 다음 수정 작업의 우선순위를 간단히 제안한다.

SEO·운영·배포 체계 전체에 대한 별도 감사로 범위를 넓히지 않는다.
다만 11개 관점의 결함을 설명하는 데 필요한 관련 설정은 확인한다.
보고서를 저장하거나 수정을 시작하지 않고 대화 내 보고로 마친다.
